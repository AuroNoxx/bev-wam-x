# 后续受控消融：算子与 MoT（2026-11-15）

当前实际环境为 PyTorch 2.11.0+rocm7.14.0 / HIP7.14.60850；SDPA与torch.compile API存在不等于该设备/形状已支持或更快。当前训练基线已使用BF16 mixed；此前融合GRU报MIOpen错误，不能继续假定通用CUDA优化在本机成立。不安装依赖、不改驱动、安全或全局设置。

在当前串行容量/历史矩阵完成后，优先比较现有SDPA默认调度与math后端的前反向、BF16与FP32输出/梯度差异；记录具体形状、warmup、计时及显存。进一步compile必须区分编译冷启动和稳态收益，完整图失败则明确记录；不把单算子加速宣称为全训练加速。保持数值误差门槛、相同数据/随机性，验证checkpoint和因果测试后才考虑接入正式入口。

MoT候选是任务/模态token分工，不是多头注意力的同义词。后续先做最小确定性路由：OCC/世界表征token一组FFN专家、轨迹动作token一组FFN专家，保留显式跨类信息交换和共享attention；与稠密融合基线比较，不一开始加入大量稀疏top-k专家。必须分别报告总参数、每类token激活参数、路由规则、token数、负载、实际FLOPs估计、optimizer/激活显存和端到端延迟。总参数匹配与激活预算匹配是不同对照，分开呈现。动态路由后续才考虑，须监测专家塌缩、溢出/丢token和负载损失。

公平实验沿用共同有效训练窗口、相同有效batch/更新数、候选数和Flow积分步数，报告世界预测及动作生成各自表现、罕见场景、安全接管。稀疏/分专家并不自动提高单卡或Orin速度，调度与访存可能抵消收益；当前未实现MoT，不宣称已经加速。输入仍严格为历史+预测未来，真实未来只在监督支路。

## 最新决定覆盖以上实施次序

用户明确先做稠密融合教师并通过验证，再考虑 MoE/MoT。当前不实现或运行任何专家架构，仅保留上述后续研究方向；当前工作只涉及数据、算子可行性和稠密教师容量。
## 本轮矩阵比较口径

- 155M/291M及约493M稠密教师，统一8个train窗口，历史4帧和11帧在共同窗口重建。未来仅作标签；末4帧与原缓存逐像素一致。只检查历史段ego位姿有限及单帧位移<8m，不能替代全面teleport/对象身份认证或源级未来融合审计。
- 有效batch=8，物理batch2/4/8通过梯度累积对齐更新数，但JEPA方差损失在microbatch内估计，故不同物理batch的优化目标并非严格等价。跨batch只用于资源判断；历史质量只能看同一物理batch且同预算，仍仅16步训练集诊断，无泛化结论。
- 每配置端到端计时包含模型创建/搬运、前后固定seed采样诊断和16步优化；不含全量磁盘读取、正式checkpoint保存、验证集评估或CARLA。重建数据一次共享。首次算子编译与缓存预热使不同配置冷启动成本不可直接当稳定性能比较。
- 纯热优化吞吐和每配置完整计时分别报告；不以显存空闲为理由无限扩展模型或全量长训。正式入口仍应保留现有Lightning、StatefulDataLoader和VerifiedCheckpointIO，当前探针故意不写模型权重。
