# Mini-WA-JEPA：从 MetaDrive 到 3D 赛车游戏

## 0. 项目目标

本项目旨在实现一个基于 BEV（鸟瞰视图）的轻量世界模型与驾驶决策系统。

**最终目标：先在 MetaDrive 中训练并验证能够自主闭环驾驶的 BEV 模型，再尝试将学到的驾驶能力迁移到 3D 赛车游戏中。**

本项目借鉴 JEPA 的潜空间预测思想，不追求完整复现 WA-JEPA，不依赖其代码或预训练权重。模型、数据管线和训练流程由本项目自行实现。

项目路线：

1. MetaDrive 环境与 BEV 数据验证。
2. 建立专家数据集和驾驶基线。
3. 单独验证未来潜空间预测。
4. 联合训练世界预测与轨迹预测。
5. 测试遮挡、丢帧和恢复驾驶能力。
6. 实现动作条件世界预测。
7. 使用 Flow Matching 生成候选轨迹，并进行风险评估与规划。
8. 完成 MetaDrive 端到端闭环驾驶验收。
9. 将 BEV 驾驶能力迁移到 3D 赛车游戏。

项目最终需要回答两个问题：

- 学习未来潜空间表征，能否真正改善驾驶决策？
- 在 MetaDrive 中学到的驾驶能力，能否迁移到新的赛车游戏环境？

不预设实验一定成功。所有结论必须由实际对照实验和闭环测试支持。

## 1. 工程要求

### 1.1 硬件自动检测

项目不得绑定某一种 GPU 厂商、型号或固定显存容量。

启动时自动检测：

- CPU、GPU 厂商和型号。
- GPU 总显存及当前可用显存。
- 系统内存。
- PyTorch 版本和可用计算后端。
- CUDA / ROCm / HIP 等相关运行时信息。
- 可用的混合精度、注意力实现和硬件优化算子。

检测结果应在启动日志中清晰展示，并保存到实验记录中。

如果没有可用 GPU，应根据实际环境选择 CPU 等兼容后端，并明确提示性能限制。

### 1.2 硬件自适应与训练参数自动校准

训练开始前，根据实际硬件和可用资源自动选择合适的训练参数，不绑定固定显卡型号或显存容量。

1. 检测 GPU 型号、计算后端、可用显存及系统内存。
2. 通过小规模前向、反向传播测试，逐步测试不同 Batch Size，测量峰值显存、训练速度和数值稳定性。
3. 综合显存余量、训练吞吐量和训练目标，选择稳定且高效的 Batch Size，不以最大 Batch Size 为目标。
4. 自动推荐混合精度、梯度累积、梯度检查点和数据加载参数，并验证其兼容性。
5. 正式训练开始后，固定并记录 Batch Size、精度、优化器、学习率及其他影响训练结果的参数，保证实验可复现。
6. 允许用户手动覆盖自动推荐的参数，但必须记录最终配置。

### 1.3 自动选择硬件后端与优化算子

根据当前硬件、驱动、运行时和已安装的软件包，优先使用 GPU 厂商提供的高性能算子及计算库，充分利用硬件加速能力。

- **NVIDIA：** 优先使用兼容的 CUDA 优化算子及 NVIDIA 计算库。
- **AMD：** 优先使用兼容的 ROCm / HIP 优化算子及 AMD 计算库。
- **其他硬件：** 优先使用对应厂商提供的兼容优化实现。

算子选择原则：

1. **优先厂商优化实现：** 对 Attention、矩阵乘法、卷积等主要计算路径，优先使用当前硬件支持的高性能算子。
2. **自动检测兼容性：** 启动时检查算子是否已安装、是否支持当前 GPU、数据类型和张量形状，并通过实际运行测试确认可用。
3. **PyTorch 原生回退：** 厂商优化算子不可用、运行失败或性能不佳时，回退到 PyTorch 原生算子及其自动调度的兼容后端。
4. **性能验证：** 通过基准测试比较执行速度、峰值显存、数值误差和稳定性，不得仅凭厂商或算子名称认定其性能更好。
5. **保留通用实现：** 不得将特定厂商的算子作为模型的强制依赖，确保模型能够在不同硬件上运行。
6. **模型兼容：** 算子切换不得改变模型结构、参数形状或检查点格式。加载已有权重后，先进行输出一致性和性能测试。
7. **记录实际配置：** 记录最终使用的算子、计算后端、精度、性能数据及回退原因。

### 1.4 显存管理与 OOM 恢复

**核心要求：自动适配当前设备，在合理使用可用资源的同时避免 OOM，并保证训练过程可恢复。**

1. 不设置固定显存使用上限，根据实际可用显存和训练负载动态选择参数。
2. 正式训练前完成资源校准，确保所选配置能够稳定执行前向传播、反向传播和优化器更新。
3. 正式训练期间保持 Batch Size 等关键参数不变，不得静默修改训练配置。
4. 发生 OOM 时，保存最近的有效检查点，记录错误及当时的资源占用。
5. 必要时自动降低 Batch Size、启用兼容的混合精度或梯度检查点，并重新验证配置。
6. 如果必须改变 Batch Size，应记录配置变化，并从检查点恢复训练；涉及 VICReg 等依赖 Batch 统计量的损失时，必须评估其对训练结果的影响。
7. OOM 恢复设置最大重试次数。超过上限后，输出明确的诊断信息和建议，不得无限重试或假报成功。
8. 检查点应尽可能保存模型、优化器、学习率调度器、训练步数和随机状态。
9. 区分显存不足、系统内存不足、算子不兼容和数值异常，不得将所有错误统一按 OOM 处理。

### 1.5 工程与实验纪律

- 配置使用 YAML 或 dataclass。
- 记录随机种子、配置、Git commit、模型检查点和评估指标。
- 数据集必须划分训练集、验证集和测试集。
- 每个阶段完成后，汇报结果、失败案例、已知限制和下一阶段建议。
- 未经确认，不得跳过当前阶段直接开发后续阶段。
- 不以模型规模或技术名词的数量作为项目成功标准。

## 2. 当前模型设计

### 2.1 BEV 输入

当前使用 MetaDrive 生成的四通道语义 BEV。

- 分辨率：128 × 128。
- 覆盖范围：自车周围约 64m × 64m。
- 连续输入：4 帧。
- 坐标系：自车居中，车头方向固定朝上。
- 通道语义和顺序：以实际代码为准。

所有数据处理、训练和评估必须保持 BEV 坐标、通道顺序、物理尺度与无效区域定义一致。

### 2.2 世界预测分支

- 根据历史 BEV 预测未来 4 个时刻的潜空间 Token。
- 不重建 RGB 图像或未来 BEV 栅格。
- 使用潜空间预测损失及 VICReg 方差、协方差正则。
- 通过实际实验检查表征是否塌缩，以及预测能力是否优于简单基线。

### 2.3 轨迹预测分支

- 预测未来 10 个路点，覆盖约 2 秒。
- 每个路点包含 `(x, y, v, heading)`。
- 当前使用确定性轨迹回归。
- 后续阶段尝试使用 Flow Matching 生成多种候选轨迹。

### 2.4 底层控制

- 横向控制：Adaptive Pure Pursuit。
- 纵向控制：速度前馈与 PID。
- 模型预测轨迹，控制器将轨迹转换为仿真器能够执行的控制量。

本项目的主路线不要求神经网络一开始就直接输出方向盘、油门和刹车。优先完成自主规划轨迹、控制器执行、仿真器反馈的闭环系统。

## 3. 分阶段执行计划

## 阶段 1：环境与 BEV 验证

**目标：** 确认计算环境、MetaDrive 仿真和 BEV 数据链路正常。

任务：

1. 验证硬件自动检测、计算后端和基本张量运算。
2. 验证 MetaDrive 的无头运行、车辆状态读取和 BEV 生成。
3. 检查 BEV 的朝向、坐标、分辨率和通道语义。
4. 验证数据采集和保存流程。

验收标准：

- 仿真能够稳定运行。
- BEV 样本通过检查。
- 数据可以连续采集并复现。
- 记录环境依赖和实际运行限制。

## 阶段 2：专家数据与驾驶基线

**目标：** 建立可靠的训练数据和可量化的驾驶基线。

任务：

1. 采集 BEV、自车状态、未来轨迹、实际控制动作，以及碰撞、越界和 Episode 终止标签。
2. 通过可控扰动采集偏离道路、障碍物干扰和恢复驾驶的数据。
3. 训练 CNN / ResNet 轨迹回归基线。
4. 按地图、Episode 或随机种子隔离训练集、验证集和测试集。

验收标准：

- 数据和时间标签正确对齐。
- 记录 ADE/FDE、路线完成率、碰撞率、越界率和推理延迟。
- 保存可复现的测试集和评估结果。

## 阶段 3：单独验证未来潜空间预测

**目标：** 验证模型能否预测未来潜变量，而不是简单复制当前状态或发生表征塌缩。

任务：

1. 使用历史 BEV 预测未来潜空间表征。
2. 监控预测损失、通道方差、协方差和有效秩。
3. 与复制最后一帧潜变量等简单基线比较。
4. 保存训练曲线和表征健康度指标。

验收标准：

- 训练过程稳定。
- 表征没有明显塌缩。
- 预测能力优于简单基线，或明确分析失败原因。

## 阶段 4：联合世界预测与轨迹预测

**目标：** 验证未来潜空间预测能否改善轨迹预测，并完成初步闭环驾驶。

任务：

1. 输入 4 帧历史 BEV。
2. 同时预测未来 4 个时刻的潜变量和未来 10 个轨迹点。
3. 联合训练世界预测损失与轨迹预测损失。
4. 与仅使用轨迹损失训练的模型进行消融对照。
5. 完成开环预测和 MetaDrive 闭环驾驶评估。

验收标准：

- 报告 ADE/FDE、路线完成率、碰撞率、越界率和推理延迟。
- 比较联合训练与仅轨迹训练的效果。
- 保存预测轨迹、真实轨迹、闭环记录和失败案例。
- 正式训练、消融和评估结果完整可复现。

## 阶段 5：遮挡与丢帧压力测试

**目标：** 验证历史信息和未来预测能否改善 BEV 不完整时的驾驶表现。

任务：

1. 加入 BEV 遮挡、道路边界缺失和连续丢帧。
2. 比较 Mini-WA-JEPA 与 CNN / ResNet 基线。
3. 测试突发障碍物、边界不可见和车辆恢复驾驶等场景。
4. 保存失败回放、预测轨迹与真实结果。

验收标准：

- 报告不同退化程度下的完成率、碰撞率、越界率和轨迹误差。
- 验证世界预测是否带来可重复的鲁棒性增益。
- 如果没有改善，先分析原因，不直接增加新模块。

## 阶段 6：动作条件世界预测

**目标：** 让模型学会预测不同驾驶方案分别会造成什么未来。

2026-10-19 用户已授权开始阶段6，并要求 chapter 的简化交互改造安排在阶段6之后；改造限制在 marimo 内，不增加框架。
本阶段先交付模型、对照与真实后果验证，以下面向初学者的 chapter 交互要求作为后续排期，不据此提前启动界面改造。

当前世界预测分支主要根据历史 BEV 预测未来潜变量。本阶段让它显式接收候选轨迹作为条件。

任务：

1. 保留历史 BEV Encoder。
2. 扩展 Predictor，使其同时接收历史场景表征和候选轨迹。
3. 在 MetaDrive 中记录实际执行的轨迹或控制序列，以及执行后产生的未来状态。
4. 将动作与未来 BEV / 潜变量严格对齐，训练动作条件预测。
5. 比较不同候选轨迹对应的预测结果与仿真器实际结果。
6. 与不使用动作条件的世界预测基线进行对照。

第一版继续使用未来 10 个路点作为高层动作条件，不强制改成底层控制量。

主可视化应将同一场景的所有候选轨迹及各自未来预测放在同一画面中比较，使用稳定候选 ID 和统一时间轴。
面向初学者的主交付是中文交互式学习场景；“播放”指可暂停、单步、拖动进度或自动推进，不要求制作视频。
通过直接操作、画面联动和分步解释帮助理解；各章围绕本章原理设计，不把所有阶段都改成预测演示。
用真实场景、路线、选中标记、执行结果解释行为；代码配中文注释按需展开，专业工具用于底层记录与研究诊断。
阶段6的实验指定轨迹须标为“实验指定”；真实评分/选择器尚未实现时，选择结果保持缺失。
潜变量热图作为辅助诊断，不能替代用户要求的规划过程主视图。详见 `docs/PLANNING_VISUALIZATION.md`。

验收标准：

- 不同候选轨迹能够产生合理、可区分的未来预测。
- 预测结果与真实仿真结果具有可验证的一致性。
- 模型能够可靠预测动作后果后，才进入候选轨迹规划阶段。

## 阶段 7：Flow Matching 轨迹生成与候选规划

**目标：** 让模型能够生成多种可能的驾驶轨迹，并利用未来预测和风险评价选择更好的方案。

Flow Matching 是本阶段计划尝试的生成方法。它不是前置阶段的必需条件，也不要求替换当前基线后就默认获得性能提升。

### 7.1 Flow Matching 轨迹生成

任务：

1. 保留现有 MSE 轨迹预测头作为对照基线。
2. 尝试使用 Flow Matching 生成未来 10 个路点组成的轨迹序列。
3. 以历史 BEV 和现有潜空间表征作为条件，学习从噪声生成合理驾驶轨迹。
4. 通过不同初始噪声生成多条候选轨迹。
5. 检查轨迹的连续性、可行驶性、速度变化和推理延迟。

Flow Matching 的目标是生成多样化的候选轨迹，而不是直接判断哪条轨迹最安全。

### 7.2 风险预测

任务：

1. 使用 MetaDrive 的真实碰撞和越界结果作为监督标签。
2. 增加轻量风险预测头，估计候选轨迹的碰撞与越界风险。
3. 验证风险预测与实际仿真结果的一致性。
4. 结合 BEV 几何信息检查道路边界和静态障碍物。
5. 对动态交通参与者，考虑其未来位置和运动趋势。

潜变量本身不能直接视为可读的碰撞结果，需要经过验证的风险预测头或明确的几何检查机制。

### 7.3 候选轨迹规划

任务：

1. 生成多条候选轨迹。
2. 根据动作条件世界预测，估计不同候选轨迹对应的未来。
3. 根据碰撞风险、越界风险、赛道进度、速度和轨迹平滑度构造可解释的评分函数。
4. 选择得分较高的轨迹。
5. 将选定轨迹交给现有 Pure Pursuit + PID 控制器执行。
6. 与直接执行原始 Action Head 输出的方案进行闭环对照。

主交互画面须可逐步或自动展现：当前场景 → 所有候选及实际评分 → 高亮选中的候选 → 车辆执行 →
实际行驶轨迹与下一帧重新预测/选择。所有候选、所选候选和实际执行轨迹必须可在同一主视图辨认，
不能仅交付若干独立预测图或潜变量热图。评分/选择来源、候选 ID、仿真步和执行结果均须可追溯，
并通过公共 RerunLogger 记录；交互回放使用同一条真实记录，不要求为教学界面另制视频。

验收标准：

- Flow Matching 生成的轨迹合理且具有足够多样性。
- 风险预测与实际结果进行独立验证。
- 比较 MSE 轨迹头与 Flow Matching 在轨迹质量、推理延迟和闭环驾驶表现上的差异。
- 验证候选规划是否确实改善驾驶表现。

如果 Flow Matching 没有带来实际增益，应保留更简单有效的方案，不强制使用生成模型。

**本阶段不要求引入强化学习。** 评分函数和规划器负责评价、比较与选择候选轨迹，不等于强化学习。

## 阶段 8：MetaDrive 完整闭环验收

**目标：** 在迁移到赛车游戏之前，确认整套系统能够稳定、自主、可重复地驾驶。

最终闭环：

历史 BEV → 世界预测与轨迹生成 → 动作条件未来预测 → 风险评估与候选轨迹选择 → Pure Pursuit / PID → MetaDrive 执行 → 下一帧 BEV。

任务：

1. 在未见测试地图和多个随机种子上测试。
2. 测试动态交通与 BEV 退化场景。
3. 比较 CNN / ResNet 基线、联合预测模型和候选轨迹规划器。
4. 记录 BEV、预测轨迹、候选方案、风险分数、控制量及真实仿真结果。
5. 确保推理过程中没有使用真实未来 BEV 或其他未来真值。

验收标准：

- 系统无需人工接管即可闭环运行。
- 多次测试具有可重复的结果。
- 报告完成率、碰撞率、越界率、行驶进度、推理延迟和失败原因。
- 所有关键指标均有基线对照。
- 完成完整实验报告。

**阶段 8 是进入赛车游戏迁移前的强制验收关卡。**

## 阶段 9：迁移到 3D 赛车游戏（最终阶段）

**目标：** 验证 MetaDrive 中学到的 BEV 驾驶能力能否迁移到实际运行的 3D 赛车游戏。

### 9.1 选择目标游戏

选择可以稳定启动、重复重置场景、接收键盘或控制器输入，并且能够在当前硬件上运行的赛车游戏。

先验证画面读取、控制输入、状态重置和测试可重复性。根据实际接口选择游戏，不预设必须使用某一款。

### 9.2 建立游戏 BEV Adapter

将游戏环境转换成与 MetaDrive 模型兼容的 BEV。

需要对齐：

- BEV 分辨率和通道顺序。
- 自车中心与朝向。
- 物理距离和像素尺度。
- 道路边界、可行驶区域、车辆和障碍物语义。

如果使用游戏内部地图或车辆状态生成 BEV，必须明确标注为特权状态测试。这只能验证模型与游戏物理、控制接口之间的兼容性，不代表已经完成从游戏画面到 BEV 的感知迁移。

随后尝试从游戏画面提取赛道、边界和车辆，生成兼容 BEV。

### 9.3 迁移与适配

按以下顺序执行：

1. **零样本迁移：** 冻结 MetaDrive 模型，直接在游戏中测试。
2. **接口适配：** 排查 BEV 语义、坐标、尺度和控制映射差异。
3. **少量数据适配：** 如果零样本迁移失败，再采集少量游戏数据进行微调。
4. **闭环验证：** 在相同起点和赛道条件下重复测试。

如果游戏只支持键盘控制，通过独立的控制 Adapter 将轨迹跟踪器输出映射为按键和持续时间，并记录控制频率与延迟。

不要将游戏特有逻辑写死在模型中，保持 BEV Provider 和控制 Adapter 可替换。

### 9.4 最终验收

- 在目标赛车游戏中完成可重复的闭环驾驶测试。
- 报告路线或圈数完成率、碰撞或驶离赛道次数、控制延迟和失败案例。
- 对比零样本迁移与适配后的效果。
- 条件允许时，与不使用世界预测的轨迹基线进行比较。
- 交付模型权重、BEV Adapter、控制 Adapter、运行说明、测试记录和失效分析。

**阶段 9 即为整个项目的最终目标。** 不默认继续扩展到通用机器人、真实道路驾驶或大型通用世界模型。

## 4. 必做对照实验

1. CNN / ResNet 轨迹回归基线。
2. 联合世界预测与轨迹预测，对比仅使用轨迹损失训练。
3. 干净 BEV，对比遮挡和丢帧 BEV。
4. 无动作条件世界预测，对比动作条件世界预测。
5. MSE 轨迹回归，对比 Flow Matching 轨迹生成。
6. 直接执行轨迹头输出，对比风险评分与候选轨迹规划。
7. 赛车游戏零样本迁移，对比少量数据适配后的结果。

所有对照使用合理一致的数据划分、测试种子和调参预算。不得只展示成功案例。

---

## 5. 数据与评估纪律

- 测试地图、Episode 和随机种子不得参与训练或模型选择。
- 未来 BEV / 潜变量只能作为训练目标或离线评估标签，推理时不得访问未来真值。
- 动作条件预测必须保证动作序列与实际未来状态正确对齐。
- 开环预测误差与闭环驾驶效果必须分别报告。
- 失败样本应根据任务保留，用于世界预测、风险分类或失败分析。
- 所有结果记录测试样本数、随机种子、模型版本和运行配置。
- 使用游戏内部状态生成 BEV 时，必须区分特权状态验证与真实画面感知迁移。
- 训练和推理应记录实际使用的硬件后端、精度、峰值显存和吞吐量。
